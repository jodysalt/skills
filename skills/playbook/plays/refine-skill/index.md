# Refine skill

Improve one existing skill, or an `add-{foo}` `refine-{foo}` pair, in place: explore, report what can go before what is missing, interview, edit. Leave the result uncommitted. Works the same on the boilerplate `add-skill` just wrote and on a skill that has drifted from the skills around it. It never creates a skill; a path that is missing is `jodysalt:playbook add-skill`'s. In a playbook repo the skill is a play behind a helper, and its helper and its entry in the play index are kept in step with it.

## Skill

The arguments passed to the play.

One skill name, or two names forming a pair, `add-{foo} refine-{foo}`, refined together in one interview, since a hand-off has two ends. If empty, `ls {dir}` and ask which, one option per skill; in a playbook repo, `ls skills/playbook/plays`, one option per play.

## Steps

1. **Target and guard.** The root is `git rev-parse --show-toplevel`, else the working directory. There are three targets, checked in this order. A playbook repo, where the root holds `.claude-plugin/plugin.json` and `skills/playbook/`: `{dir}` is `skills`, the skill is the play at `skills/playbook/plays/{name}/index.md` behind its helper at `skills/{name}/SKILL.md`, with its entry in the play index, the list after `Plays – ` in the `description:` line of `skills/playbook/SKILL.md`, and it runs as `/{plugin}:{name}` or `/{plugin}:playbook {name}`, `{plugin}` being the manifest's `name`; a `_{name}` play has no helper and no index entry. A plugin repo without `skills/playbook/`: when the root holds `.claude-plugin/plugin.json`, `{dir}` is `skills` and a skill runs as `/{plugin}:{name}`, `{plugin}` being the manifest's `name`. Any other repo: otherwise `{dir}` is `.claude/skills`, the skill is at `.claude/skills/{name}/SKILL.md`, and it runs as `/{name}`. If `{dir}/{name}/SKILL.md` is missing for a name given, stop and point at `jodysalt:playbook add-skill`; nothing is written. In a playbook repo `{name}` resolves to `skills/playbook/plays/{name}/index.md` instead, with the same stop, pointing at `jodysalt:playbook add-skill`, when that is missing; the name `playbook` resolves to `skills/playbook/SKILL.md`, refined as a skill is in a plugin repo without `skills/playbook/`, with no helper and no index entry of its own.
2. **Branch gate.** If the current branch does not match `planning-<YYYY-MM-DD>` followed by anything and `docs/tickets/open/<branch>/` does not exist, offer to invoke `jodysalt:playbook start-planning-session {name}`, the first name given; on yes pass it and ask nothing else. Continue on the current branch if the user declines. Skip if the gate already ran this conversation. Either way, the root is `git rev-parse --show-toplevel` from here on.
3. **Explore before asking.** Read the skill, `CLAUDE.md`, `docs/glossary.md` when it exists, a missing or template-only file counting as an empty glossary, the *Product principles* of `docs/vision.md` when it exists, every skill the skill names and every skill naming it (`grep -l '{name}' {dir}/*/SKILL.md`), the skill's row in `README.md` when a table there links `skills/*/SKILL.md`, and `start-planning-session`'s description when the skill holds a branch gate. Recommended answers come from these, and each defined term is used in its defined sense, never redefined in passing; a term the glossary lacks is used as the skill uses it. In a playbook repo, read the play in place of the skill, with its helper `skills/{name}/SKILL.md` and the play index; the plays the play names and the plays naming it (`grep -l '{name}' skills/playbook/plays/*/index.md`) in place of the skills; and the play's row in `README.md` when a table there links `skills/playbook/plays/*/index.md`.
4. **Report findings before editing anything**, removals first, each named by the step, rule or line it is about:
   - What can go: a step or rule restating what a skill it invokes already does; a rule no step needs; a sentence repeating the lead; a frontmatter field no step needs; a template prompt or `TODO:` still standing.
   - The frontmatter: a description not in its three parts – what it does and where it writes, the "Use when" phrases with `/{name}`, what it never does; a `name` not equal to the directory; an `argument-hint` with no argument section, or the reverse.
   - The pair and the partners: an `add-{foo}` whose steps do not end by handing off to `refine-{foo}`, or that fills in, validates or reports what the refine should; a `refine-{foo}` with no `add-{foo}`, or the reverse; and each partner the skill implies that `{dir}` lacks – `remove-{foo}` for an `add-{foo}`, and whatever else its job implies – named as a suggestion for `jodysalt:playbook add-skill`, never drafted here.
   - Callers out of step: a hand-off worded differently at its two ends; `start-planning-session`'s description missing this skill when it gates; a `README.md` row that is not the description's first sentence.
   - A term used in a sense the glossary does not define.

   In a playbook repo two findings change. The helper is checked in place of the three-part description, a play having no frontmatter: a `name` not equal to the directory; a `description` that is not one sentence, or still the template's prompt; `disable-model-invocation: true` missing; a body that is not the one line invoking `{plugin}:playbook {name}` followed by the arguments placeholder with the Skill tool; an `argument-hint` that does not agree with the play's argument section, present with no section or the reverse. And the play's entry in the play index is checked: missing, out of alphabetical position, or holding more than one trigger. A `_` play with a helper or an index entry is a finding. The finding about a `README.md` row that is not the description's first sentence applies only outside a playbook repo.
5. **Interview** by invoking the `grill-me` skill from this plugin (`jodysalt:playbook grill-me`) with the subject "the skill at `{dir}/{name}/SKILL.md`", both paths for a pair; in a playbook repo the subject is "the play at `skills/playbook/plays/{name}/index.md`, its helper and its entry in the play index". Give it this framing:
   - Seed the decision tree with the findings from step 4, removals asked before additions, then add the decisions the skill makes without saying so.
   - The codebase, `CLAUDE.md` and the skills under `{dir}` count as explorable; a question they answer is never asked.
   - Only an answer the user agrees to lands, a removal like an addition. A run where the user declines every question leaves the file byte for byte unchanged.
   - Edit `SKILL.md` as answers land; when a hand-off changes, edit the pair's other file in the same answer, so its two ends never disagree. Another skill is named the way it is invoked: `{plugin}:{name}` for a plugin skill, the bare name for a sibling under `{dir}`. A frontmatter field beyond `name`, `description` and `argument-hint` appears only when a step needs it: `disable-model-invocation` for side effects a stray mention must not trigger, `context: fork` for work that should not share the caller's context. Anything in a skill outside the pair is surfaced for a `refine-skill` run on it.
   - In a playbook repo, edit the play's `index.md` as answers land, and name another play the way it is invoked there, `{plugin}:playbook {name}`. The helper and the index entry mirror the play, so each is edited in the same answer that changes what it mirrors: the helper's `description` when what the play does or where it writes changes, its `argument-hint` when the argument section changes, the entry's trigger when the phrase that starts the play changes. The helper keeps its shape, its frontmatter fixed and its body one line; a `_` play has neither to edit. Where a trigger changes, follow the room rule the `add-skill` play holds, so the `description:` line never passes 1,536 characters by `grep -m1 '^description:' skills/playbook/SKILL.md | wc -m`, the lead sentence shortened first, then other plays' triggers, longest first, no entry dropped; shortening another play's trigger is a removal and lands only on the user's yes.
6. **Validate.** Run `claude plugin validate {dir} --strict` and fix what it reports before going on. It reads `.claude/skills/` as it reads `skills/`, and it tolerates unknown frontmatter keys. In a playbook repo `{dir}` is `skills`, as in any plugin repo.
7. **README row.** One table in `README.md` is meant per kind of repo. In a plugin repo that is not a playbook repo it is the table whose rows link `skills/*/SKILL.md`: sync the skill's row outright, adding it in alphabetical position when missing and rewriting its text to the description's first sentence when they differ. In a playbook repo it is the table whose rows link `skills/playbook/plays/*/index.md`, and no other: add the play's row in alphabetical position when missing, linking the play, with the helper's `description` as its text, and leave the text of a row that exists alone. A `_` play gets no row. In either, no table, no row. Outside a plugin repo, skip this step.
8. **Report.** What was removed and what was added, step by step; the partners step 4 suggested; the validation result; the row, when one was added or rewritten; in a playbook repo, what changed in the helper and in the index entry, and every sentence and trigger the room rule shortened; in a plugin repo, that `.claude-plugin/plugin.json` is at its current version and owes a bump the commit that lands the change should make, never made here; and how to reload the skill: `/reload-plugins` for a project skill, `claude --plugin-dir .` or `/reload-plugins` for a plugin clone registered as a local marketplace. Leave everything unstaged and suggest `jodysalt:playbook commit` (a `feat:` commit when the skill's behaviour changed, `refactor:` when only its wording did).

## Rules

- Edits the named skill or pair and its `README.md` row, and nothing else: never creates a skill, never bumps the plugin version, never touches `CLAUDE.md`, never commits. In a playbook repo that is the play, its helper, its entry in the play index and its `README.md` row; the rest of the `description:` line of `skills/playbook/SKILL.md` changes only by the room rule.
- In a playbook repo a `_{name}` play is refined as its `index.md` alone: it never gains a helper, an index entry or a `README.md` row.
- A removal needs the user's yes like an addition. Never invent content; ask, or leave a `TODO:` marker.
- Never a personal `~/.claude/skills/` target.
