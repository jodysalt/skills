# Refine landing page

Improve an existing landing page against the notes that hold its market test: explore the page, the notes and the mocks, report what the notes imply and the page lacks, interview, edit in place, and, when the test is over, record its result and the decision beside the page. Leave the result uncommitted. It never creates the page; a repo with no `docs/landing-page/index.html` is `jodysalt:add-landing-page`'s. Branch gate as a spec skill's: the market test is drafted on a planning branch and lands through `wrap-up-worktree`.

## Scope

$ARGUMENTS

If given, one of four things. One or more section names, matched case-insensitively against the page's section ids – `headline`, `hero`, `benefits`, `price`, `cta`, `faq`, `terms` – and `README.md`'s `##` headings – `hypothesis`, `metric`, `threshold`, `window`, `call to action`; the findings and the interview cover only those sections. A mock slug, with or without its `mock-` prefix, matching `mocks/mock-{slug}.html`; the findings and the interview cover only that mock. Or `result`, which runs the findings and then step 8. Or `look`, which runs the findings and asks only step 6's Look branch, on a page whose look is set as well, re-asking the accent and the mood with the page's own values recommended; `refine-landing-page look benefits` combines it with section names as the others combine. If empty, the whole page. If a name matches nothing, list the names and ask.

## Steps

1. **Root and guard.** The root is `git rev-parse --show-toplevel`, else the working directory. If `docs/landing-page/index.html` is missing under it, stop and point at `jodysalt:add-landing-page`; this skill improves a page, it never creates one, and nothing is written. Read `docs/glossary.md` when it exists, a missing or template-only file counting as an empty glossary, and use each defined term in its defined sense in the edits and the report, never redefining one in passing; a term the glossary lacks is used as the input uses it.
2. **Branch gate.** If the current branch does not match `planning-<YYYY-MM-DD>` followed by anything (a pre-upgrade `planning-2026-10-21` counts), offer to invoke `jodysalt:start-planning-session landing-page`; on yes pass it and ask nothing else. When `git status --porcelain docs/landing-page` prints anything, the offer says those edits stay in the current checkout, since the worktree forks from the last commit, and that declining keeps working on them where they are. Continue on the current branch if the user declines. Skip if the gate already ran this conversation. Either way, the root is `git rev-parse --show-toplevel` from here on.
3. **Serve the page.** Serve it locally, so the user watches each edit land on a reload:
   - Look for a server already serving this repo's page: `pgrep -f "http-server {root}/docs/landing-page"`, `{root}` absolute so two repos' pages are told apart.
   - Found, take its port from `lsof -nP -iTCP -sTCP:LISTEN -a -p {pid}`; the URL is `http://127.0.0.1:{port}/`. The match is usually the shell or `npm exec` that launched the server, and the listener a descendant that renamed itself `http-server`, so when the match holds no listener `{pid}` walks down its children (`pgrep -P {pid}`) until one does.
   - Else, when `command -v npx` finds it, run `npx --yes http-server {root}/docs/landing-page -a 127.0.0.1 -c-1 > {scratchpad}/landing-page-server.log 2>&1` in the background – the Bash tool's `run_in_background`, a driver without it appending `&` – wait a few seconds, and read the URL from the log: the first `http://127.0.0.1:` line after `Available on:`.
   - Print the URL as one line before the findings.
   - With no `npx`, or no such line in the log, print `npx --yes http-server docs/landing-page -a 127.0.0.1 -c-1` for the user to run and carry on; nothing else waits on the server, and the findings, the interview, the edits and the mocks are the same without it.
   - The server is left running for the session; nothing in this skill stops it.
4. **Explore before asking.** Read `docs/landing-page/index.html`, `docs/landing-page/README.md` when present, `docs/landing-page/mocks/index.html`, `docs/landing-page/mocks/mock.css` and every `docs/landing-page/mocks/mock-*.html` when present, and `ls docs/landing-page/mock-*.png` for the screenshots on disk. Take today's date from `date +%F`. Recommended answers come from these.
5. **Report findings before editing anything.** Each finding is named by the section, file or slug it is about:
   - Each of the seven section ids the page lacks – `#headline`, `#hero`, `#benefits`, `#price`, `#cta`, `#faq`, `#terms` – and `README.md` missing, or each of its five `##` headings – `Hypothesis`, `Metric`, `Threshold`, `Window`, `Call to action` – missing or empty. The two the page mirrors are cross-checked against it: `## Call to action` naming a link that differs from a filled `href` on `#cta`'s `<a>` (an empty one is the next finding, reported once), and `## Hypothesis` claiming a benefit no `<h3>` in `#benefits` names.
   - `#cta`'s `<a>` with `href=""` or no `href`.
   - `#hero` with no `<img>`, and each benefit – an `<h3>` in `#benefits` – with no `<img>` before the next `<h3>` or the section's end.
   - Each `<img src>` on the page or in `mocks/index.html` with no file on disk at `docs/landing-page/mock-{slug}.png`; and each `mocks/mock-{slug}.html` with no row in `mocks/index.html` or no `<img>` on the page pointing at its screenshot.
   - `## Result` or `## Decision` still holding its `TODO:` prompt once today's date, from `date +%F` in step 4, is past the end date in `## Window`, the end date read as the last `YYYY-MM-DD` in that section, else the last date it can read; a window whose end date cannot be read is its own finding.
   - The `/* TODO: look */` marker in `index.html` or `mocks/mock.css`, reported as "look not set".
   - Each `README.md` section still holding its `TODO:` prompt – the line under its heading starting `TODO:` – named by its heading, the `## Result` and `## Decision` prompts aside. A `## Window` holding its prompt is this finding alone, never the unreadable-end-date finding above.
   - Any other `TODO:` in the page, `README.md`, `mocks/mock.css` or a mock, the `## Result` and `## Decision` prompts aside: those are the window finding above once the window has ended and the right state until then.

   With `result`, the findings are reported and step 8 follows, the interview covering only the result.
6. **Interview.** Invoke the `grill-me` skill from this plugin (`jodysalt:grill-me`) with the subject "the landing page at `docs/landing-page/index.html` and its market test at `docs/landing-page/README.md`". Give it this framing:
   - Seed the decision tree with the findings from step 5, then add the decisions the page makes without saying so: a price with no terms, a FAQ that skips an objection the terms imply, a headline that promises what no benefit backs.
   - Branches, in this order, each asked only when a finding or the scope raises it – every branch on a fresh boilerplate, only its section on a scoped run, the remaining ones when a stopped run resumes, since its remaining `TODO:`s still fire. The idea the recommended answers draw on is the caller's framing when it gave one ("the idea is: {idea}"), else the page's own copy. Each question quotes the `TODO:` it fills, and its answer lands as the edit that replaces that placeholder:
     - **Offer** – raised by a `TODO:` in the nav, `#headline`, `#benefits`, `#price`, `#cta`, `#faq` or `#terms`: the product's name, for the nav wordmark and the footer's brand line (recommended from the idea, else the repo name); who it is for, the eyebrow; the headline (recommended: leads with the loss or longing the hypothesis tests, never the category); the subhead beneath it (recommended: the mechanism in one sentence); the one benefit, then up to two more (three recommended; each an outcome for its card's `h3` with a concrete scene for its `p`, the lede what the product is in one sentence, and the section `h2`s promises in the audience's words); the three steps (recommended: the user's first hour, the strip's title naming it); the price (a figure recommended, with its unit, the sentence saying what it buys and when it is charged, and the four checks what is included; "none yet" replaces the card with a plain sentence saying the price is not set); the call to action – its kind, which is the button's text and the nav button's, its link and its terms, the `#cta` `h2` an invitation – landing on the button, the nav button, the terms line and `README.md`'s `## Call to action`, with this warning: the recommended answer is an honest waitlist or a real pre-order with its terms on the page, never the fake "out of stock" after a buy click, since ad platforms treat a misleading destination as misrepresentation and this skill cannot certify a page against any advertiser's policy; where the user gives no link, the `href` is left empty for the findings; the objections the FAQ answers (recommended: the ones the terms imply – when it ships, what happens to the money, how to cancel – the answers naming real costs and dates, the same facts as `#terms`'s three lines).
     - **Look** – raised by the "look not set" finding or by `look` in the scope: the accent – one hex, recommended from the audience the eyebrow names: a sea green such as `#0b7a75` for coastal, outdoor and travel products, a deep blue such as `#1d4ed8` for finance and B2B software, a warm orange such as `#c2410c` for food and hospitality, a plum such as `#6d28d9` for creative tools; on *dark ink* a brighter hue of the same family, such as `#3b82f6` for a blue, since the accent sits on dark surfaces – the question quoting the current `--accent`; then the mood – one of *warm paper* (consumer, outdoors and craft products; the template's defaults, so a page that keeps it still has its marker removed), *cool white* (software, B2B) and *dark ink* (developer tools, finance) – the question quoting the current `--surface`. The mood's eight lines are copied from the set below, never re-derived; `--gold` and `--serif` are fixed, never asked and never changed:
       - *warm paper*: `--surface: #f7f4ed; --surface-deep: #efe9dd; --panel: #fffdf8; --ink: #0e1b21; --ink-soft: #33444c; --muted: #6a7980; --line: rgba(14, 27, 33, 0.12); --line-strong: rgba(14, 27, 33, 0.22);`
       - *cool white*: `--surface: #f8fafc; --surface-deep: #eef2f6; --panel: #ffffff; --ink: #0f172a; --ink-soft: #334155; --muted: #64748b; --line: rgba(15, 23, 42, 0.12); --line-strong: rgba(15, 23, 42, 0.22);`
       - *dark ink*: `--surface: #0f1419; --surface-deep: #151b22; --panel: #1a222b; --ink: #eef1f4; --ink-soft: #c5ced6; --muted: #8b98a5; --line: rgba(238, 241, 244, 0.12); --line-strong: rgba(238, 241, 244, 0.22);`
       - The accent's three lines, the hex the only value typed, the mood picking the mixing partner and no computed hex written: `--accent: {hex};`, then `--accent-deep: color-mix(in srgb, var(--accent) 70%, black);` for *warm paper* and *cool white* and `--accent-deep: color-mix(in srgb, var(--accent) 70%, white);` for *dark ink*, then `--accent-mist: color-mix(in srgb, var(--accent) 18%, var(--surface));` for every mood.
       - As the two answers land, the `:root` block of `docs/landing-page/index.html` and of `docs/landing-page/mocks/mock.css` get the same eleven value lines – the mood's eight, the accent's three – in place of the ones there, and the `/* TODO: look */` line is removed from both files; nothing outside either `:root` changes, and in *dark ink* the call-to-action band, the phone bezel and the shadows going light is the mood, not a defect. A page whose `:root` lacks the thirteen tokens – one `0.22.0` wrote – predates the design language: the branch says so and asks nothing. With `look` in the scope on a page whose look is set, the recommended answers are the page's own – the current `--accent`, and the mood whose `--surface` the page holds – and the same edit lands in both files, with nothing to remove.
     - **Screens** – raised by `#hero` or a benefit with no `<img>`: every benefit gets a screen (recommended: one per benefit, the first the hero, the picture under the headline); then one question per screen – its short name, whose kebab-case form is its `{slug}`; what it shows and in what state (a filled dashboard, an empty first run, a confirmation after the action); which benefit it illustrates; desktop (screenshot `1280,800`) or phone (`390,844`), phone recommended for the hero since the template stages it in a phone bezel, desktop for the others, a desktop hero getting `class="desktop"` on its `<img>`. The first screen's question says it is the hero, and its slug is the `{hero-slug}` `og:image` names. Each lands by replacing the hero's or the card's `<!-- TODO: … -->` comment with `<img src="mock-{slug}.png" alt="…">`, the `alt` its one-line description, and running step 7 for that screen. A deferred answer leaves the screen a `TODO:` sentence in its mock, and the mock is still written.
     - **Test** – raised by a `README.md` section still holding its prompt: the hypothesis (one sentence a result can falsify; recommended from the headline and the one benefit); the metric (what is measured at the link the call to action gives – sign-ups, pre-orders, clicks – recommended: the conversion of visits to that action); the threshold (a number the hypothesis passes at); the window (start and end dates; recommended: from the day the page goes live, fourteen days); each landing in its `README.md` section in place of the prompt.
     - **Analytics** – raised by the head's `<!-- TODO: analytics … -->` comment: an optional snippet, recommended none; when supplied it replaces that comment verbatim, the last thing before `</head>`, never edited; when none, the comment is removed.
   - The page, the notes, the mocks and the screenshots from step 4 count as explorable; a question they answer is never asked, and each recommended answer cites what it came from.
   - Only an answer the user agrees to lands. A run where the user declines every question leaves every file under `docs/landing-page/` byte for byte unchanged.
   - Edit `docs/landing-page/index.html` and `docs/landing-page/README.md` as answers land, keeping the house design language the template fixes: the section ids and their order (`#headline`, `#hero`, `#benefits`, `#price`, `#cta`, `#faq`, `#terms`), the template's tokens, components and 54rem breakpoint as they are, their values the Look branch's, inline CSS only, no `<link>` and no `<script>` but a user-supplied analytics snippet; an added card, step, checklist item or FAQ pair copies the template's markup for one, and a removed one goes whole; every `<img src>` a bare `mock-{slug}.png` beside the page; `og:title` and `og:description` following the headline and the subhead, and `og:url` plus `og:image` written as `https://{user}.github.io/{repo}/` and `https://{user}.github.io/{repo}/mock-{hero-slug}.png` when the hero lands and `git remote get-url origin` matches `github.com[:/]{user}/{repo}(.git)?` – no match, neither tag – `og:image` following the hero when it changes after that; `<html lang>` changed only when the copy that lands is in another language. Each `TODO:` goes as its answer lands; a deferred answer stays a `TODO:` marker in its section, written there when the page holds none.
   - When an answer needs a screen the page does not have, or changes what a screen shows, ask for that screen as the Screens branch does: its short name, whose kebab-case form is its `{slug}`; what it shows and in what state; which benefit it illustrates; desktop (`1280,800`) or phone (`390,844`). Run step 7 for that one screen as the answer lands, adding or correcting the page's `<img src="mock-{slug}.png" alt="…">` – in place of the card's comment or after that benefit's `<p>`, or inside `#hero` when the screen is the hero. When the finding is a screenshot missing for a mock that exists, ask only its size and run step 7 for that screen, which leaves the mock untouched and takes the picture.
   - When the user says the test is over, run step 8.
   - `docs/glossary.md` is read, never written.
7. **Write the mocks.** When the answer rewrites a screen whose `mocks/mock-{slug}.html` exists, that one file is removed first so the step below writes it afresh, and its `<li>` in `mocks/index.html` is rewritten when its name or description changed; every other mock, `mock.css` and `mocks/index.html` beyond that row keep the never-overwrite rule below, and a re-taken screenshot overwrites the `.png`, which is what the command does. For each screen, in order, with its slug, name, description, state and size (`{w},{h}`), write the mock that fakes it and take its screenshot, one screen finished before the next:
   - Write `docs/landing-page/mocks/mock-{slug}.html`, creating the folder: one self-contained page faking that screen in that state – `<!doctype html>`, `<html lang="…">` in the page's language, `<meta charset="utf-8">`, the viewport meta `width=device-width, initial-scale=1`, a `<title>` holding the screen's name, `<link rel="stylesheet" href="mock.css">`, no `<script>`, realistic placeholder content in the product's own words, and the whole screen inside the window at the chosen size so the screenshot is the screen and nothing else. A screen whose description is a `TODO:` holds that sentence in place of the content, and the mock is still written. When `mock-{slug}.html` already exists it is left untouched, byte for byte, and the run says so; the row and the screenshot still happen.
   - With the first mock, when they are missing: `docs/landing-page/mocks/mock.css` – `body` at `margin: 0`, the font stack `system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`, a `min-height: 100vh` frame, a neutral palette and a handful of classes every mock shares (a top bar, a card, a button, a table), a short file the mocks lean on rather than restyle; and `docs/landing-page/mocks/index.html` – `<!doctype html>`, `<html lang="…">` in the page's language, `<meta charset="utf-8">`, `<title>Mocks</title>`, the same `<link rel="stylesheet" href="mock.css">`, an `<h1>`, and one `<ul>`. Both are left untouched when present.
   - Append `<li><a href="mock-{slug}.html">{screen name}</a> <img src="../mock-{slug}.png" alt="{screen description}"></li>` to that `<ul>` unless the index already holds a row for `mock-{slug}.html`.
   - Find a browser: `command -v google-chrome chrome chromium`, taking the first hit; none, and on macOS `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` exists, take that. With a browser, run from the root `"{chrome}" --headless --screenshot=docs/landing-page/mock-{slug}.png --window-size={w},{h} docs/landing-page/mocks/mock-{slug}.html`, `{w},{h}` the screen's size. Without one, or when the command exits non-zero or leaves no file, print that one command with `google-chrome` as the binary for the user to run and carry on; the mock, its row and the page that points at `mock-{slug}.png` are written either way, and nothing is installed.
8. **Record the result.** With `result`, or when the user says the test is over, ask through the same interview for the metric's value at the window's end – no recommended answer, the number is the user's – then write `## Result` in `docs/landing-page/README.md` as one line: the metric, its value, the threshold and whether it was met. Then ask the decision, the three options the prompt's own – `build`, `change the offer`, `stop` – recommended `build` when the threshold was met, `stop` when it was not, and `change the offer` when the interview finds the page misrepresented the idea rather than the idea failing; write `## Decision` as that one word or phrase and a sentence of why. A `## Result` already filled is shown as it stands and rewritten only when the answer says so.
9. **Report.** The URL from step 3 and `{url}mocks/` for the mocks index, or that the page was not served and the command to serve it – `npx --yes http-server docs/landing-page -a 127.0.0.1 -c-1`; the findings resolved and those left open; when the Look branch ran, the mood and the accent it set (`look: dark ink, #3b82f6`) and that the `:root` blocks of `docs/landing-page/index.html` and `docs/landing-page/mocks/mock.css` hold them; when the `/* TODO: look */` marker is still in `index.html` or `mocks/mock.css`, that the look is not set and `refine-landing-page look` sets it; the files edited (`docs/landing-page/index.html`, `docs/landing-page/README.md`); each mock written or rewritten as `mocks/mock-{slug}.html`, `mocks/mock.css` and `mocks/index.html` when this run created them, and each screenshot taken at `docs/landing-page/mock-{slug}.png`. For each screenshot not taken, the one command to run – `google-chrome --headless --screenshot=docs/landing-page/mock-{slug}.png --window-size={w},{h} docs/landing-page/mocks/mock-{slug}.html` – saying the page already points at `mock-{slug}.png` and, once, that a macOS user substitutes `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` for `google-chrome`. When the result was recorded, say that `## Result` and `## Decision` now hold it and that `jodysalt:refine-vision` cites them. Say that everything is uncommitted and suggest `jodysalt:commit` – a `feat:` commit when the page or a mock changed, a `docs:` commit when only the notes did.

## Rules

- Never creates `docs/landing-page/index.html`; a missing page stops the run before anything is written.
- Writes nothing outside `docs/landing-page/`.
- Never edits `.github/workflows/landing-page.yml`.
- Rewrites only the mock the answer names; `mock.css`, `mocks/index.html` beyond that mock's row, and every other mock are never overwritten.
- The screenshot command and the server (`http-server`) are the only programs run beyond `git` and `date`; the server's npm cache download is the only install, and nothing is written into the repo.
- Never invents copy, a result or a decision; asks, or leaves a `TODO:` marker.
- Never pushes, never commits, never enables GitHub Pages, never picks a payment, form or analytics provider.
- Reads `docs/glossary.md` and never writes it.
