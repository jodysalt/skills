## Outcome
A user types `/jodysalt:deliver-brief <brief>` in a directory, empty or not, and comes back to a `main` that holds the result, ready to review: a repo with the workflow's layout, a filled `docs/vision.md`, the brief's work drafted, implemented task by task and closed, and a green full suite, with no human turn in between. `deliver-brief` sizes the brief the way `add-initiative` and `add-ticket` already do, through a scout stage that explores the repo first and recommends, the judge's twin fed a brief instead of an initiative, while the root only ratifies: one shippable change becomes a single ticket of the right type, with no bet, no initiative and no judge, closed when its tasks are done and the suite passes, a single `feat` tags the open initiative that fits, and with none it stands on its own, drafted by `add-ticket` with no initiative, as a person would when a feature needs no wider push; an outcome that needs several tickets becomes a bet and an initiative, worked one ticket at a time: `deliver-brief` drafts the ticket that moves the outcome most, breaks it down, runs the loop, wraps it up, then reads the initiative again and drafts the next. After each ticket a fresh sub-agent judges every bullet in the initiative's `## Success metrics` met or not: all met closes the initiative, any unmet picks the next ticket, a `spike` when it cannot tell which ticket moves the metrics or the brief needs facts the repo does not hold, and a cap on tickets per run, spikes included and fixed in the `jarvis` ticket, stops the run with a report instead. Nothing is planned further ahead than the ticket in hand, so every ticket is written against the code as it is. When there is no repository, `deliver-brief` runs `git init`, scaffolds, and makes one `chore:` commit on `main` so there is something to branch from, the one thing the scaffold refuses to do. A repo with code but no layout gets the scaffold as a planning session of its own, one `chore:` commit merged into `main`, before anything else. A scaffolded `docs/vision.md` still holding the template prompts counts as fresh and is filled from the brief. A run starts from the main checkout, as `add-worktree` requires, so a brief given from inside a worktree stops with a pointer at `exit-worktree`. It is a new skill that drives the existing chain rather than a new chain, and it follows the flow a person follows: docs are drafted on a `planning-<date>` branch through `start-planning-session`, `refine-vision`, `add-initiative`, `add-ticket`, `add-tasks` and `close-initiative`; code lands on a ticket branch through `add-worktree`, `complete-tasks` and `wrap-up-ticket`; every branch ends with `squash-commits`, so it reaches `main` as one commit through a new `merge-worktree` skill, fast-forward only, after which `remove-worktrees` clears the worktree and its branch so the next planning branch forks from a current `main`. Every skill runs as it does today, apart from changes any user can use, `deliver-brief` plays the user, and `main` changes only by merge, so `git log` on `main` reads as the run's history: one commit per planning session and one per ticket. Its root stays thin – the brief, the stage the run is at, and one short report per stage – and every stage runs in a fresh sub-agent that invokes the skill, does the work, and reports in a few lines. There is no run log: git history is the trail, so each stage's commit body carries what a person would otherwise have been told, the judge's verdict per metric and why this ticket next, the decisions taken unattended, and the checks left for the person. Interviews split by leverage, using the split `grill-me` already makes: a stage takes its own recommended answer for the trivial many on the spot and sends the vital few back to the root with their options and recommendation; the root answers them from the brief and the vision and resumes the same sub-agent, and a cap on rounds per stage, fixed in the `jarvis` ticket, stops a stuck exchange. A brief that says "like X" gets X's layout and behaviour, never its brand assets or licensed material. A check no worker can verify, a visual match or a manual step in a test plan, is neither dropped nor marked done: the final report lists it as left for the person. That report leads with the reading `deliver-brief` took of the brief and why, then the answers the root gave, so a person who meant another reading sees it first. State is the docs on `main`: the initiative's `## Tickets` list is the record, `open/` versus `closed/` is progress, and `tasks.md` is the cursor, so `/jodysalt:deliver-brief` with no brief, from the main checkout, takes the only open initiative, else stops and lists them, and resumes at the first unfinished piece: an open ticket's next pending task, in its worktree when one exists, else the next ticket to draft. A leftover worktree whose commits are not on `main` is merged first; one with uncommitted changes stops the run. Each planning stage commits its docs through `commit` before the next begins, since the loop's clean-tree check, the wrap-up guard and the merge all need a clean tree. Nothing is pushed.

Five tickets deliver it. The first is `merge-worktree`, the one skill the chain lacks, usable by hand from the day it lands. The second is a `spike` ticket type: research with a question, a time box and a `findings.md` beside `index.md` that ends in a recommendation and the tickets it implies, closed like any ticket, with its own template in `add-ticket`, its frontmatter checked by `refine-ticket`, and named as docs-only work in `add-tasks`; a spike's findings are the next ticket stage's input. The third is the `deliver-brief` skill with the lines it needs elsewhere: `grill-me` says the caller's framing decides who answers, so a stage declared unattended takes its own recommendation as the user's answer for the trivial many and sends the vital few back to the caller. `add-ticket` lets a `feat` stand alone when the user says it does, and `refine-ticket` stops flagging one. The throwaway-repo run checks it. The fourth is `wrap-up-worktree`, which lands a finished worktree on `main` in one command – closing its ticket when the branch is one, squashing, merging and removing it – so `deliver-brief`'s root runs one skill at the end of every branch in place of the `wrap-up-ticket` stage and the squash, exit, merge and remove tail, and `wrap-up-ticket` retires. The fifth is the docs that teach the workflow about `deliver-brief`, the README's Workflow paragraph and the `CLAUDE.md` block `setup-skills` writes, and `deliver-brief` drafts and delivers that one itself when it picks this initiative up.

## Why now
The *Hands-off delivery* bet in `vision.md`. The loop already runs unattended, but everything above it – vision, initiative, ticket – still needs a human at every question, so a run lasts as long as a person's attention. *One Command Adoption* left a repo one scaffold and one interview away from planning; the same repo is now one command away from a delivered branch, because every skill in the chain is invocable by name and takes explicit arguments. What is missing is a driver: nothing turns a brief into the next ticket, nothing carries the docs from a planning branch to a ticket branch without a human merge, and every skill stops for a pick or a branch gate. The *Driver-agnostic* principle says the skills need no `deliver-brief` mode for that; the driver does the answering, and the few changes it needs serve any user. Long runs also need the root context kept free and the heavy lifting in sub-agents, and Claude Code now allows the layout: sub-agents nest three deep below the root, run the Skill tool, inherit the root's working directory, and resume with their context intact.

## Success metrics
- In an empty directory with the plugin installed, `/jodysalt:deliver-brief <brief>` for a small app ends, with no human turn, with `main` holding the layout, a filled `vision.md`, every ticket the run drafted closed and a passing full suite; `git log` on `main` shows one squashed commit per planning session and one per ticket, and no worktree is left behind.
- The root's transcript for that run holds no skill body and no worker report: only the stage reports and the answers the root gave.
- Interrupting the run mid-ticket and running `/jodysalt:deliver-brief` again resumes in that ticket's worktree at its next pending task and redoes no finished task.
- In this repo, `/jodysalt:deliver-brief` with no brief picks up this initiative, drafts its last ticket, the docs, and delivers it unattended.

## Non-goals
- Pushing or opening PRs. `main` changes only by fast-forward merge through `merge-worktree`; a merge that cannot fast-forward stops the run rather than inventing a merge commit or a rebase. Reviewing `main` afterwards is the human's.
- Asking the human anything. The brief is the whole input; a run's questions are answered by a stage or by the root, never by a person.
- Retrying, re-planning or rolling back a failed task. The loop's first failure ends the run, as `complete-tasks` does today, with a report naming the branch, the worktree and the stage; the docs stay as they were, so a resume or a person can carry on. Running `/jodysalt:deliver-brief` again after a failure is the person choosing to retry: the resume runs the failed task with a fresh worker.
- Parallel workers or parallel tickets. Entries and tickets are dependency-ordered and run one at a time.
- A `deliver-brief` mode in any skill. What a skill asks, it asks the same way whoever drives it; the most a skill changes is what any user can use: the `grill-me` line on who answers, and `add-ticket` letting a `feat` stand alone.
- A runner outside Claude Code: no shell script of headless invocations, no Agent SDK orchestrator.
- Eval suites for `deliver-brief`. It runs unattended, so the *Evals for the risky skills* bet owes it one; that lands with that bet's initiative, and the throwaway-repo run is the check here.
- Stopping to ask when the vision has no bet for the brief. `deliver-brief` adds one, and the review on the branch is where a person objects.
