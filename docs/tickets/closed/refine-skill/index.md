# Goal
A skill in this plugin can always be refined the way a ticket, the vision or a landing page can: `refine-skill` revisits an existing `SKILL.md`, reports what can go and what is out of step, interviews and edits in place, and `add-skill` becomes the add half of that pair – it writes the boilerplate and hands off to `refine-skill` in the same session – so the two share no steps. Both run the branch gate first, so a skill is never edited on the base by accident, and `add-skill` drafts an `add-{foo}` with its `refine-{foo}` and names the partners it implies.

Rules: edits the named skill or pair and the `README.md` row only; never creates a skill, never bumps the version, never touches `CLAUDE.md`, never commits; a removal needs the user's yes like an addition. Description in three parts, with "refine the X skill", "the X skill should Y", "tidy up the X skill", `/refine-skill`.

## Strategic fit
Stands on *Add, then refine*: `add-skill` and `refine-skill` are the pair the principle describes, and `add-skill` is where the principle propagates, since every pair the method gains is drafted through it. Stands on *Branches before `main`*, giving the two skills that write source the branch gate, and on *Trim with the 80/20 principle*, since `refine-skill` reports removals before additions and `add-skill` loses the four steps the refine does. Stands on *Dogfooding*: the plugin's own skills get the refine path every other spec in the method has. Respects *A home for standalone skills*: the method calls `refine-skill` from `add-skill`.
