# Goal
A user types `/jodysalt:jarvis <brief>` in a directory, empty or not, and comes back to a `main` ready to review: the workflow's layout, a filled `docs/vision.md`, the brief's work drafted, implemented task by task and closed, and a green full suite, with no human turn in between. Run again with no brief, it resumes where the docs say it stopped. It drives the existing chain the way a person does, playing the user at every question, so no skill gains a jarvis mode and `git log` on `main` reads as the run's history.

# Context
- Builds on the `spike` ticket type, the initiative's second ticket, now closed as `docs/tickets/closed/spike-ticket-type/`: the judge picks a spike when it cannot tell which ticket moves the metrics, and `add-ticket`, `refine-ticket` and `add-tasks` already carry `type: spike` with its `findings.md`, so this ticket lands complete with one version bump.
- The design is the initiative's `## Outcome`: the scout, the one-ticket-at-a-time loop, the judge, the branch flow, the thin root, git history as the trail, the interview split, the report and the resume rules are all fixed there. This ticket fixes what it delegates, the caps, who switches checkouts, the stage prompt and the report, and changes nothing it settled.
- The chain, every skill invocable by name with explicit arguments: `setup-skills`, `start-planning-session`, `refine-vision`, `add-initiative`, `add-ticket`, `add-tasks`, `commit`, `squash-commits`, `exit-worktree`, `merge-worktree`, `remove-worktrees`, `add-worktree`, `enter-worktree`, `complete-tasks`, `wrap-up-ticket` and `close-initiative`. The docs skills already interview through `grill-me`, whose 80/20 pass splits the vital few from the trivial many, and the tail already goes out as assumptions with the answer it would take.
- `setup-skills` never runs `git init` and never commits. `add-worktree` and `merge-worktree` run from the main checkout, and `merge-worktree`'s dirty-main guard counts untracked files, so a run can leave nothing untracked in the main checkout. `complete-tasks` stops on its first failed task with a clean tree or a report of a dirty one.
- Claude Code: sub-agents nest three deep below the root, and the deepest path here is root, `complete-tasks` stage, `complete-task` worker. They run the Skill tool, inherit the root's working directory, and resume with their context intact when messaged again, which is how a stage gets its vital answers back. `EnterWorktree` from a sub-agent moves only that agent.

# Scope

In:
- One new skill, `skills/jarvis/SKILL.md`, run as `/jodysalt:jarvis [brief]`, plus its README table row and the plugin version bump.
- The stages, each a fresh sub-agent that invokes one skill, does the work and reports in a few lines: scout, `refine-vision`, `add-initiative`, `add-ticket`, `add-tasks`, `complete-tasks`, `wrap-up-ticket`, judge and `close-initiative`. The scout is the sizing judge `add-initiative` and `add-ticket` already apply, fed the brief and the repo; the judge reads the initiative's `## Success metrics` after each ticket and names the next ticket, a spike, or done.
- The root: holds the brief, the stage the run is at and one report per stage; switches checkouts; answers a stage's vital few from the brief and the vision and resumes that stage; commits each planning stage through `commit`; squashes, merges and removes each branch; and prints the final report.
- Directory states: no repository, empty or holding files, gets `git init -b main`, the scaffold and one `chore:` commit on `main` that takes everything present; a repo with code but no layout gets the scaffold as a planning session of its own, one `chore:` commit merged; a `docs/vision.md` still holding the template prompts is filled from the brief.
- Resume: `/jodysalt:jarvis` with no brief, from the main checkout, takes the only open initiative, else stops and lists them, and continues at the first unfinished piece. A leftover worktree whose commits are not on `main` is merged first; one with uncommitted changes stops the run.
- The two caps, and the stops the initiative names: a brief from inside a worktree, a merge that cannot fast-forward, the loop's first failed task. A lone `feat` with no open initiative that fits does not stop the run: jarvis follows the workflow as a person would and has `add-ticket` draft it as a `feat` that stands on its own, with no initiative.
- One line in `grill-me`: the caller's framing decides who answers.
- `add-ticket` lets a `feat` stand alone: when no open initiative fits and the user says the feature stands on its own, it drafts the `feat` with no `initiative:`. `refine-ticket` stops flagging a `feat` without one.

Out:
- The initiative's non-goals: pushing or PRs, asking the human, retrying or rolling back a failed task, parallel workers or tickets, a jarvis mode in any skill, a runner outside Claude Code, eval suites for jarvis, stopping when the vision has no bet for the brief.
- The `spike` ticket type, the initiative's second ticket, and the docs that teach the workflow about jarvis, its fourth.

# Acceptance criteria
- In an empty directory with the plugin installed, `/jodysalt:jarvis <brief>` for the small app in the test plan ends with no human turn, and `main` holds the layout, a filled `vision.md`, the app's one `feat` ticket closed with no initiative, and a passing full suite; `git log` on `main` shows one squashed commit per planning session and one per ticket, and no worktree or branch is left behind.
- The root's transcript for that run holds no skill body and no worker report: only the stage reports and the answers the root gave.
- Each planning stage's commit body carries what a person would otherwise have been told: the judge's verdict per metric and why this ticket next, the decisions taken unattended, and the checks left for the person.
- The final report leads with the reading jarvis took of the brief and why, then the answers the root gave, then every check left for the person: a visual match or a manual step in a test plan is neither dropped nor marked done. On a failure it names the branch, the worktree and the stage.
- Interrupting the run mid-ticket and running `/jodysalt:jarvis` again from the main checkout resumes in that ticket's worktree at its next pending task and redoes no finished task.
- A brief that is one shippable change lands as a single ticket of the right type with no bet, no initiative and no judge, closed when its tasks are done and the suite passes. A lone `feat` with no open initiative that fits lands the same way, as a `feat` ticket with no `initiative:`.
- The run stops with a report, docs as they were, when: it is started from inside a worktree; the main checkout is dirty at the start; no brief is given and there is not exactly one open initiative; a leftover worktree has uncommitted changes; a branch cannot fast-forward into `main`; the loop's first task fails; a stage is still asking after 3 rounds; or a run reaches 5 tickets.
- A brief that says "like X" gets X's layout and behaviour, never its brand assets or licensed material.
- Nothing is pushed or fetched at any point.
- `grill-me` says in one line that the caller's framing decides who answers; `add-ticket` drafts a `feat` with no `initiative:` when no open initiative fits and the user says it stands on its own; `refine-ticket` no longer flags that; and no other skill changes.
- `README.md` has a row for `jarvis`, `plugin.json` is `0.3.0`, and both `claude plugin validate` commands pass with `--strict`.

# Implementation notes
- One file, `skills/jarvis/SKILL.md`, in the shape of the family: frontmatter with `name`, a `description` naming the trigger phrases "run jarvis", "deliver this brief", "jarvis, build X" and `/jarvis` and stating no human turn, resumes from the docs, never pushes; an `argument-hint` of `"[the brief – empty resumes the only open initiative, from the main checkout]"`; a `## Brief` section; Steps; Rules. One stage-prompt template parameterised by skill name and argument, not a prompt per stage. Stage sub-agents and their workers inherit the root's model; no override.
- The root switches checkouts itself: `start-planning-session`, `add-worktree`, `enter-worktree`, `exit-worktree`, `merge-worktree` and `remove-worktrees` run in the root, a few tool calls each, and every stage sub-agent inherits the root's checkout. Claude Code's `EnterWorktree` from a sub-agent moves only that agent, so a stage that switched would leave the root, and its own workers, somewhere else.
- Two caps, constants in the skill body: 5 tickets per run, spikes included, after which the run stops with a report; 3 interview rounds per stage, a round being one exchange of vital questions and answers between a stage and the root, after which the stage is stuck and the run stops. A bet-sized brief needs two to four tickets, so five leaves room for a spike; three rounds covers a ticket's vital few with one to spare.
- The stage prompt declares the run unattended, so `grill-me`'s line applies; names the skill to invoke and its argument; forbids pushing; and asks for a report of a few lines that ends either with "done" or with the vital few questions, each with its options and a recommendation. The root answers them from the brief and the vision, and when both are silent takes the stage's recommendation and says so in that stage's commit body, then resumes the same sub-agent with its context intact. The third exchange without "done" stops the run.
- The order of a run. (1) Guards: the session is the main checkout, else stop pointing at `exit-worktree`; `git status --porcelain` there is empty, else stop pointing at commit or stash, since `merge-worktree` would refuse later. (2) Directory state: no repository gets `git init -b main`, `setup-skills` and one `chore:` commit through `commit` that takes everything present, files that were already there included, because anything left untracked trips the dirty-main guard, and a stop from `commit` on a secret or a build artefact ends the run with that report; a repo without the layout gets `start-planning-session`, `setup-skills`, `commit`, `squash-commits`, `exit-worktree`, `merge-worktree`, `remove-worktrees`. (3) With a brief, the scout stage: explores the repo and the brief and reports the reading it took and why, and the sizing, one shippable change with its type or a bet and an initiative. With no brief, the resume rules instead: the only open initiative, else stop and list them; then a leftover worktree with commits not on `main` is merged and removed, one with uncommitted changes stops the run, and the run continues at an open ticket's next pending task, in its worktree when one exists, else at the next ticket to draft. (4) Planning session: `start-planning-session`; `refine-vision` when `docs/vision.md` still holds template prompts or, for a bet-sized brief, has no bet for it; `add-initiative` for a bet-sized brief; `add-ticket`; `add-tasks`; `commit` (`docs:`); `squash-commits`; `exit-worktree`; `merge-worktree`; `remove-worktrees`. (5) Ticket: `add-worktree <slug>`, `enter-worktree`, the `complete-tasks` stage, the `wrap-up-ticket` stage, `squash-commits`, `exit-worktree`, `merge-worktree`, `remove-worktrees`. A lone ticket ends here. (6) Judge stage, bet-sized briefs only: a fresh sub-agent reads the initiative's `## Success metrics` and reports each met or unmet, and next either the ticket that moves the metrics most, a spike when it cannot tell or the brief needs facts the repo does not hold, or done. All met: a planning session with `close-initiative`, `commit`, `squash-commits`, `exit-worktree`, `merge-worktree`, `remove-worktrees`. Otherwise back to (4), the verdict and the reason for the pick going in that session's commit body; the fifth ticket ends the run with a report instead. (7) The final report: the scout's reading and why, the answers the root gave, the checks left for the person; on a stop, the branch, the worktree and the stage.
- `grill-me` gains one line under `## Rules`: the caller's framing decides who answers; a caller that declares the run unattended takes the recommended answer as the user's for the trivial many and sends the vital few back to the caller, each with its options and recommendation.
- `add-ticket` step 3 gains a third answer for a `feat` with no open initiative that fits, beside escalating to `add-initiative` and pushing back: the user says it stands on its own, and it is drafted with no `initiative:`; step 6's frontmatter rule and the description follow. `refine-ticket` step 4 stops reporting a `feat` without `initiative:` as a finding. No other skill changes.
- A README row between `grill-me` and `list-worktrees`, in the table's style; the Workflow paragraph and the `CLAUDE.md` block stay with the fourth ticket. `plugin.json` to `0.3.0`, a new skill being a minor bump under the vision's rule.

## Strategic fit
The outcome of `hands-off-delivery` is this skill; `merge-worktree` and the `spike` type exist to serve it, and the fourth ticket is the first thing it delivers. It is the *Hands-off delivery* bet in `vision.md` made real: one command from a brief to a `main` ready for review. It serves *Driver-agnostic*, since jarvis plays the user and every skill runs unchanged; *Explore before asking*, since the scout explores before sizing and only the vital few reach the root; and *One thing, then stop*, since each stage does one skill's job and nothing is pushed. It answers the *Unattended work needs structure* problem for the layers above the loop. It respects the initiative's non-goals, no push, no human question, no jarvis mode in a skill, and the vision's *A runner outside Claude Code* stays out by leaning on sub-agents and the Skill tool.
