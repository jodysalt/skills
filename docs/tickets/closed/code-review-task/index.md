# Goal
A ticket's backlog ends with a review of the branch against the repo's own coding standards, so the code the loop lands meets `docs/coding-standards.md` without a human reading the diff for style. The review is itself a task: a fresh worker diffs the branch against its base and, for each breach of the standards, appends a refactor task the loop then implements. The standards are enforced by the same unattended loop that wrote the code, and the human's return-and-inspect pass starts from code that already meets them. The standards file is part of the layout `setup-skills` scaffolds, and `refine-coding-standards` fills it in through an interview the way `refine-vision` fills in `docs/vision.md`, so a repo has the file from day one and writes its standards when it is ready.

# Context
- `skills/add-tasks/SKILL.md` fixes the entry shape (an H2 heading plus `- **category:**`, `- **status:**` and `- **steps:**` bullets, with `- **notes:**` a fourth bullet only the loop's workers write), drafts entries one Ralph iteration each, and in step 3 appends exactly one completion gate, `## Run full test suite for {slug}`, after the implementation tasks. The gate is skipped for docs-only work and `type: spike` tickets, where the last task is a review against the ticket's acceptance criteria instead. Step 4 dedups by H2 heading; the skill is append-only and touches nothing but the ticket's `tasks.md` and a spike's missing `findings.md`.
- `skills/complete-task/SKILL.md` runs in a fresh context: step 2 reads the entry's `steps`, `category` and `notes`, the sibling `index.md`, the initiative and `CLAUDE.md`; step 5 hands notes over to later pending entries; step 6 flips the status line and touches nothing else in `tasks.md` beyond what step 5 wrote; step 7 commits once via `commit`, staging the task's files plus `tasks.md`, and reverts the flip and the notes when the commit fails for good; step 8 reports the heading, what changed, the judgment calls and the headings annotated. Its `description` says it never changes a second task's status or steps, and its Rules say it never changes a later entry's heading, `category`, `status` or `steps`. All of that landed with the closed `task-handover-notes` ticket.
- `skills/complete-tasks/SKILL.md` re-reads `tasks.md` after every worker and picks the first `pending` entry, so entries a worker appends are picked up on the next iteration with no change to the loop. Its check after a worker is the noted entry `done` and a clean tree, which appended entries committed with the task satisfy. Its worker prompt already asks for the later task headings the worker left notes on, and its summary carries the workers' judgment calls.
- `skills/squash-commits/SKILL.md` already resolves a branch's base the way every worktree skill does: the branch the main checkout has checked out, `git -C <main checkout> branch --show-current` with the main checkout the first path in `git worktree list`, and `git merge-base <base> HEAD` as the fork point. The review's diff is that range.
- `close-ticket` and `wrap-up-worktree` guard only on `- **status:**`; `deliver-brief` runs an `add-tasks` stage then a `complete-tasks` stage and reads only their reports, and it answers no to every offer of another skill a root-run skill makes, `setup-skills` offering `refine-vision` among them. None needs a change.
- `skills/setup-skills/SKILL.md` is one idempotent pass with no interview and no branch gate: it creates only what is missing, writes `docs/vision.md` from a template whose section bodies are prompts for `refine-vision`, and ends by offering `jodysalt:refine-vision`. It creates no `docs/coding-standards.md`, and no repo this plugin scaffolded holds one, this one included. The first user's repo, already scaffolded, gets a missing file from a second run.
- `skills/refine-vision/SKILL.md` is the pattern for filling a scaffolded file in: a branch gate, explore the repo before asking, report which sections still hold the template's prompt, quoted in the skill so it reads no other, then `grill-me` seeded with the findings, editing as answers land; it never creates the file and never commits. `start-planning-session`'s `description` names the skills that escalate to it for the gate.
- `skills/add-skill/SKILL.md` fixes the house style for a new skill: frontmatter `name`, a three-part `description` and `argument-hint`; a body of one paragraph, an argument section, numbered steps and rules; one `SKILL.md` with no supporting files; a README table row in alphabetical position; `claude plugin validate skills --strict`.
- `plugin.json` is `0.6.0`; the version bumps on any change to a skill's behaviour. `README.md`'s `add-tasks` row says it ends the list with a full-suite gate, its `setup-skills` row lists what the scaffold creates, and its skills table has one row per skill. `claude plugin validate .` and `claude plugin validate skills --strict` gate the manifest and frontmatter; `--strict` on the root fails on the warning about `CLAUDE.md` at the plugin root, so the manifest gate runs without it.

# Scope

In:
- `add-tasks` appends the review task only when `docs/coding-standards.md` exists and holds at least one `## ` heading, each `## ` section being one standard. When the file is missing, or holds no `## ` heading because it is still the template, no review task is appended and the report says which; a repo opts in by writing its first standard, through `refine-coding-standards` or by hand. One grep, no marker sentence.
- The review worker appends the refactor entries itself, directly after its own entry's work, in the entry shape `add-tasks` fixes, which the review entry's steps inline so a fresh worker needs no other skill. The appended entries ride in the review task's one commit with its status flip. `add-tasks` stays ticket-only and never writes a refactor entry.
- `complete-task` gains one allowance: an entry whose steps say to append entries to `tasks.md` may append them, in the fixed shape and after every existing entry, and still changes no existing entry beyond its own status line.
- The review is the last entry `add-tasks` writes, after the full-suite gate, so the branch is green before it is reviewed. When the review finds breaches it appends the refactor entries and then one closing gate with a heading distinct from the first; when it finds none it appends nothing and the ticket ends on the review. There is no second review, so the loop always terminates.
- The review covers only the lines the branch added or changed: the diff from `git merge-base <base> HEAD` to `HEAD`, the base resolved as `squash-commits` resolves it. A pre-existing breach in a touched file but outside the diff hunks is left alone, so the refactors stay inside the ticket's own change and a one-line edit to a legacy file cannot balloon the backlog. From the main checkout on the base branch itself there is no fork point; the review says so and appends nothing.
- The review entry is a `chore` headed `## Review the branch against docs/coding-standards.md for {slug}`, appended by a new `add-tasks` step after the gate. Its steps inline everything a fresh worker needs: resolving the base, the diff range, reading `docs/coding-standards.md` and nothing else, the per-standard grouping, the entry shape, the closing gate, the no-breach case and the no-fork-point case.
- A refactor entry is one `chore` entry per standard breached, in the order the standards appear in the file, its heading naming the standard's heading, its steps listing each file and hunk to change and one narrowest check, never the full suite, which the closing gate owns. The count is bounded by the number of standards.
- The closing gate is headed `## Run full test suite for {slug} after review`, its steps copied verbatim from the first gate so the test command matches the repo. It is appended only when at least one refactor entry was.
- Docs-only and `type: spike` tickets get no review task, as they get no gate; the report says so alongside the gate.
- Running `add-tasks` again on a ticket whose review is done skips the review entry by heading, as it skips the gate today, and the report lists it as a duplicate.
- `complete-tasks`'s worker prompt asks the worker to name the headings of any entries it appended, and the loop summary lists them for the user's return-and-inspect pass. Nothing else in the loop changes.
- `README.md`'s `add-tasks` row names the review, its `setup-skills` row names the standards file, and a `refine-coding-standards` row sits in alphabetical position. The README's Workflow paragraph, the `CLAUDE.md` block `setup-skills` writes and this repo's own `CLAUDE.md` each gain one clause naming `docs/coding-standards.md`; a repo already scaffolded keeps its old block, since `setup-skills` checks for the `## Workflow` heading only. `plugin.json` to `0.7.0`.
- `setup-skills` creates `docs/coding-standards.md` from a template when it is missing, as it creates `docs/vision.md`, and ends by offering `jodysalt:refine-coding-standards` beside `jodysalt:refine-vision`. The template holds `# Coding standards` and one prompt paragraph and no `## ` heading, so a fresh file never switches the review on. A standard is one `## ` section: the heading names it, the body is the rule in a sentence or two, then one idiomatic example lifted from the repo's own code, and nothing else. One file, as `docs/vision.md` is one file: no directory and no supporting files, so the review reads one path and the standards stay the vital few. What a linter or formatter already catches is left to that tool. It stays one idempotent pass: no question and no interview inside it.
- A new `refine-coding-standards` skill, in `add-skill`'s house style, fills `docs/coding-standards.md` in and revisits it later, the way `refine-vision` does `docs/vision.md`: explore the repo, report findings, interview through `grill-me`, edit as answers land, leave the edits uncommitted. It never creates the file; a missing file points at `jodysalt:setup-skills`. It has a branch gate like `refine-vision`, and `start-planning-session`'s `description` names it among the skills that escalate there. Its argument is `refine-vision`'s: one or more standard headings matched case-insensitively against the `## ` headings, the findings and the interview covering only those; empty means the whole file; no match lists the headings and asks.
- Its recommended standards come from the repo's own code and from the idioms of any framework the manifest names. It explores before asking: `CLAUDE.md`, the manifest, every linter and formatter config, `git log --oneline -30`, and a sample of source files weighted to the most-changed paths. A candidate is a convention the code mostly follows but not always, or a framework idiom, each with its example lifted from a file that already follows it; where no file does, the skill writes a minimal example in the framework's idiom and says so. Anything a configured linter or formatter rule already enforces is never recommended.
- Its findings before the interview: the template's prompt paragraph still present, a `## ` section missing its rule or its example, a standard a linter or formatter config already enforces, and a standard the code contradicts throughout. A run where the user declines every question leaves the file byte for byte unchanged.

Out:
- An `add-coding-standards` skill, or an interview inside `setup-skills`. The template is the day-one file and `refine-coding-standards` is the one deep dive, on the fresh template and on a file that has drifted alike.
- A standards file for this repo beyond the template `setup-skills` writes; writing its standards is a `refine-coding-standards` run after the merge.
- A `docs/coding-standards/` directory with supporting files; the standards are one file, and `refine-coding-standards` edits that file only.
- Reviewing against `CLAUDE.md` when the standards file is missing. `complete-task` already reads `CLAUDE.md` for coding norms while implementing; the review enforces the standards file alone.
- `complete-task` reading `docs/coding-standards.md` before it codes. The worker reads `CLAUDE.md` for norms as today, and the review is the one place that reads the standards; a breach costs a refactor task and the closing gate, by design.
- A second source for `add-tasks`, or a findings file beside `tasks.md` that a human turns into tasks later. The review's output is the tasks themselves.
- A re-review after the refactors. One pass per `add-tasks` run; the closing gate is what checks the refactors.
- Breaches outside the diff hunks, and auditing the whole repo against the standards. The review is of the branch, not the codebase.
- A cap on refactor entries; one per standard bounds them.
- Any change to `close-ticket`, `wrap-up-worktree` or `deliver-brief`; its rule of answering no to every offer covers the new one from `setup-skills`, and it gains no `refine-coding-standards` stage, so an unattended run leaves the template as is and never gets a review.
- Eval suites; those belong to the *Evals for the risky skills* bet.

## Strategic fit
Stands on its own. It serves the *Agents drift without a spec* problem in `vision.md`: a ticket now has a written standard for how its code looks, not only for what it does, and the loop enforces it the same way every time. It serves *Unattended work needs structure* by keeping the enforcement inside the loop, as tasks that stand alone and land as one commit each, rather than as a human's style pass afterwards. It keeps *One thing, then stop*: the review task reviews and writes the backlog, and the refactors are separate tasks with their own commits. It serves *Conventions are hard to adopt* by making the standards file part of the layout `setup-skills` creates, so it exists before the first review runs. It keeps *One opinionated method* and the *A home for standalone skills* non-goal: `refine-coding-standards` is a skill the method calls, offered by `setup-skills` and enforced by the review `add-tasks` appends, and the review runs only where a repo has written the standards it enforces.
